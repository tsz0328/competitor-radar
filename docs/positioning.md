## 一、一句话定位

> **自动盯住同赛道 SaaS / App 的官网与公开页面，把"页面变了什么"翻译成"这件事对我意味着什么"。**

不是网页监测工具，不是数据爬虫平台，而是**竞品决策的情报助手**。

---

## 二、我们监控什么（对象定义）

### 2.1 监控对象

**同类型 SaaS 产品、移动 App、开发者工具的官方公开页面。**

典型竞品集合（以"协作办公"赛道为例）：

```
Notion / 飞书 / 钉钉 / 企业微信 / Confluence / Microsoft Loop / 腾讯文档 / 语雀
```

一个"竞品"在本系统中的定义是：**一个你持续关注的产品**，它下面挂若干**监控数据源**（官网首页、定价页、Changelog…）。

### 2.2 明确不监控什么

| 不做 | 原因 |
|---|---|
| **电商商品的价格 / 销量 / 评论**（淘宝、京东、拼多多、抖音等） | 需登录、有滑块与接口签名、平台 ToS 明确禁止；且商品页每次渲染都变（推荐位、促销标签），Diff 噪音极大。AI 无法绕过这些限制直接获取，硬爬会让项目重心从「AI 分析」偏移到「对抗风控」 |
| 需登录才能访问的页面 | 合规红线（`docs/architecture.md` 风险表已明确：不绕过登录验证） |
| 个人隐私数据 | 合规红线 |
| 付费数据源（天眼查 API 等） | 第一版只做公开网页信息 |
| 社媒舆情全量抓取 | 范围失控，v2 再议，且只接官方公开接口 |

> **电商方向不是放弃，是后置。** 见第六节 v2 路径。

## 三、目标用户与核心场景

### 3.1 目标用户

| 角色 | 身份特征 | 当前痛点 |
|---|---|---|
| **产品经理**（主） | 负责某条产品线，需要持续跟进 5-20 个竞品 | 每天人工刷官网、截图、贴群，效率低、易遗漏、无法发现细微变化 |
| **市场 / 战略**（次） | 需要输出竞品分析、定价对比、市场趋势 | 零散信息难提炼，写一次竞品分析要花一整天 |
| **创业团队 / 独立开发者**（次） | 没有专职竞品分析岗 | 想知道"对手这周干了什么"，但没有工具 |

**用户规模假设**：第一版面向**单用户 / 小团队**（≤5 人），不做多租户 SaaS 化。

### 3.2 三大核心场景

#### 场景一：日常监控 —— "今天有什么值得我关注的？"

```
用户每天早上打开 Dashboard
  ↓
看到：新增 8 条情报，其中 2 条高影响
  ↓
点开高影响事件 → 看到 AI 摘要 + 新旧内容 Diff + 影响判断
  ↓
3 分钟内完成今日竞品扫描
```

**关键价值**：从"我得去逛 12 个网站"变成"系统告诉我哪 2 条值得看"。

#### 场景二：周报复盘 —— "这段时间到底发生了什么？"

```
每周一自动生成周报
  ↓
核心摘要（一段话说清本周格局） + 重点变化（带 AI 影响判断） + 统计数据
  ↓
可直接转发给团队，或作为周会材料
```

**关键价值**：不是"事件复述"，而是"格局判断"——例如"本周 Notion 与飞书同时加码 AI，协作办公赛道的差异化战场已从编辑器转移到 AI 能力"。

#### 场景三：趋势判断 —— "市场往哪个方向发展？"

```
聚合近 90 天历史事件
  ↓
统计：变化频率（多久调一次价）、类型分布（主要在哪个方向发力）、节奏趋势（加快还是放缓）
  ↓
LLM 生成趋势判断："该竞品近 3 个月调价频率较前 3 个月提升一倍，且新功能集中在 AI 方向，推测正在加速抢占 AI 细分市场"
```

**关键价值**：这一步把"孤立事件"升级为"连续判断"，是整条链路里 AI 真正承担决策价值的地方。

### 3.3 用户真正买的不是"数据"，是"判断"

| 层次 | 内容 | 用户是否愿意付费 |
|---|---|---|
| 原始数据 | 网页快照、Diff 文本 | ❌ 用户自己也能看 |
| 结构化信息 | 事件分类、时间轴 | ⚠️ 有价值但可替代 |
| **业务判断** | "这件事对你意味着什么"、"市场在往哪走" | ✅ **核心付费点** |

因此系统的每一处设计都要追问一句：**这一步是在堆数据，还是在逼近判断？**

## 四、竞品边界（我们与谁的区别）

| 对比对象 | 它们做什么 | 我们不做 / 做得不同 |
|---|---|---|
| **人工巡检**（人工刷网站、截图群） | 全靠人力 | 我们自动化采集 + AI 提炼，但我们**不替代深度体验**（竞品试用、功能实测仍需人工） |
| **网页变更监测工具**（Visualping、Wachete 等） | 告诉你"这个页面变了" | 我们进一步告诉你"变的是什么类型、影响多大、对你意味着什么"，且**按竞品维度组织**而非按 URL 维度 |
| **流量/市场分析平台**（SimilarWeb 等） | 流量、排名、用户画像等宏观数据 | 我们不碰流量估算，只做**公开页面内容的变化** |
| **电商数据工具**（生意参谋、蝉妈妈等） | 商品价格、销量、评论数据 | 我们**明确不做电商商品数据**（见 2.2） |
| **通用爬虫框架** | 提供抓取能力 | 抓取只是我们的输入层，价值在下游的 Diff + LLM 分析 |

**我们的差异化**：`公开页面 → 快照 Diff → LLM 语义化 → 业务判断 → 主动呈现`。中间两段（Diff 与语义化）是护城河。

## 五、数据源白名单与黑名单

### 5.1 白名单（v1 支持）

所有数据源必须同时满足三个条件：**公开可访问、无需登录、内容可 Diff**。

| source_type | 说明 | 典型 URL | 渲染方式 | 默认频率 |
|---|---|---|---|---|
| `homepage` | 官网首页 | `https://www.notion.so/` | browser | 每天 |
| `pricing` | 定价页 | `https://www.notion.so/pricing` | browser | 每天 |
| `changelog` | 更新日志 / Release Notes | `https://www.notion.so/releases` | browser | 每天 |
| `blog` | 官方博客 | `https://www.notion.so/blog` | http（RSS 优先） | 每天 |
| `docs` | 帮助文档 | `https://www.notion.so/help/...` | browser | 每周 |
| `status` | 服务状态页 | `https://status.notion.so/` | http | 每小时 |
| `rss` | 通用 RSS / Atom | `https://www.notion.so/blog/rss.xml` | http | 每小时 |
| `app_store` | App Store / Google Play 应用页 | `https://apps.apple.com/...` | browser | 每天 |

详细的抓取策略、提取策略、Diff 策略见 `docs/data-source-design.md`。

### 5.2 黑名单（v1 与 v2 均不碰）

| 类型 | 具体问题 |
|---|---|
| 电商商品页（淘宝 / 京东 / 拼多多 / 抖音 / 快手小店）的价格、销量、评论 | 登录墙 + 滑块验证 + 接口签名 + 动态渲染 + ToS 禁止 |
| 需要登录或 Cookie 才能访问的页面 | 合规红线 |
| 需要逆向/破解接口签名的任何数据源 | 合规红线 |
| 个人隐私数据、非公开社群内容 | 合规红线 |

**判据（新增数据源前先自问）**：

1. 这个页面不登录能直接看到吗？→ 否，不做
2. 需要破解签名或绕过风控吗？→ 是，不做
3. 拿到的内容能做有意义的 Diff 吗？（会不会每次刷新都在变）→ 否，不做
4. 平台 ToS 允许吗？→ 否，不做

四个问题全过，才进白名单。

## 六、v2 路径：电商 / 商品数据以"数据源插件"形式接入

**原则：不做对抗式抓取，只接公开可得、可 Diff 的数据源。**

架构上已经预留扩展点（`backend/app/core/source_registry.py` 的 `SOURCE_TYPE_REGISTRY`），v2 新增数据源 = 注册表加一项 + 实现对应的 Fetcher/Extractor/Differ **三元组**，核心采集与分析链路零改动。

| v2 候选数据源 | 获取方式 | 为何合规可 Diff |
|---|---|---|
| `shopify_product` | DTC 独立站 / Shopify 店铺商品页 | 商品页与价格完全公开、反爬弱、结构稳定 |
| `app_store_rss` | App Store / Google Play 公开 RSS 与榜单 | 官方公开接口，含版本更新说明、评分、榜单排名 |
| `open_api` | Amazon PA-API、京东联盟等官方开放平台 | 走正规 API，需申请资质，不爬页面 |

这三类的共同点：**不依赖对抗平台风控，AI 仍然承担主要价值**。

**接入顺序建议**：先把 v1 的 8 种官网数据源跑稳（数据质量 > 数据广度），再按上述顺序扩展。

## 七、明确不做的事（v1 边界清单）

| 维度 | v1 不做 | 备注 |
|---|---|---|
| 数据范围 | 电商商品价格 / 销量 / 评论 | v2 以插件形式接入公开数据源（第六节） |
| 数据源 | 付费数据源（天眼查等） | 只做公开页面 |
| 数据源 | 社媒全量舆情抓取 | v2 再议，且只接官方公开接口 |
| AI 能力 | 自研情感分析模型 | 直接调用大模型能力 |
| 多租户 | 多用户 SaaS 化、团队协作、权限体系 | 第一版单用户 / 小团队 |
| 工程 | Alembic 迁移（开发期 `create_all`） | 里程碑 11 |
| 工程 | Celery 分布式队列 | APScheduler 足够（里程碑 10） |
| 工程 | LangChain / LangGraph | 核心链路是单次调用 + 结构化输出，框架是过度设计；v2 多 Agent 协作才引入 |
| 产品 | 竞品试用、功能实测、用户体验对比 | 需要人工深度介入，超出"公开信息监控"范畴 |
| 产品 | 流量估算、市场份额测算 | 属于流量分析平台领域，我们没有数据源 |

## 八、成功标准（v1 验收口径）

| 指标 | 目标 |
|---|---|
| 采集成功率 | 白名单数据源单次抓取成功率 ≥ 95%（连续 7 天） |
| 误报率 | 显著变化判定为"无用变化"（如导航栏轮播、时间戳）的比例 ≤ 20% |
| AI 摘要可用率 | 人工抽样 20 条事件，摘要准确反映变化内容 ≥ 80% |
| 时效性 | 从页面变化发生 → 用户在 Dashboard 看到事件 ≤ 24 小时 |
| 端到端闭环 | 无 LLM API Key 时，Mock 兜底仍能跑通「添加竞品 → 抓取 → Diff → 事件 → 周报」全链路 |

## 九、一句话自检

每当要加功能时，问自己：

> **这个功能是在帮用户更快得到"业务判断"，还是在堆更多"原始数据"？**

如果是后者，先不做。
